# HeadwayIQ

Event-aware metro headway recommendation system for Metro Hacks PS-04,
*"No Day Is an Average Day."* HeadwayIQ turns the official GMRC timetable plus
event/weather conditions into transparent, per-band headway recommendations for
the Ahmedabad Metro — and serves them through a local dashboard. It is a
**deterministic, offline prototype**: no LLM, no paid API, no cloud, no network.

## What is here

```
headwayiq/           # package (standard library only)
  schema.py          #   declarative dataset schemas (single source of truth)
  validation.py      #   deterministic, provenance-aware validation
  db.py              #   fixture loading + SQLite store
  config.py          #   tunable engine parameters (limits, multipliers)
  engine.py          #   event/weather analysis -> demand -> headway -> explanation
  scenarios.py       #   7 reproducible demo scenarios
  server.py          #   localhost dashboard (stdlib http.server)
  web/index.html     #   Kraken-styled single-page dashboard
  cli.py             #   validate / load / status / serve
data/fixtures/       # CSV sources (timetable=official GMRC; demand/events/weather=synthetic)
docs/                # data dictionary, source register, design ref, handoff
tests/               # pytest suite (data foundation + engine)
```

The runtime has **no third-party dependencies and needs no network or API
key**. `pytest` is the only dev dependency.

## Setup

```bash
python -m pip install -e ".[dev]"   # or just: python -m pip install pytest
```

## Run the dashboard

```bash
python -m headwayiq.cli serve        # http://127.0.0.1:8000  (Ctrl+C to stop)
```

Pick a scenario; the page calls the real engine and shows, per time band and
direction, the reference vs recommended headway, the action
(increase/reduce/maintain), the demand drivers, and a plain-language
explanation. Localhost-only and read-only (no auth — do not expose publicly).

## How a recommendation is made

1. **Analysis** (`engine.analyse_band`) — find the events and weather that
   actually overlap each corridor + time band; missing weather is flagged, never
   assumed clear.
2. **Demand estimation** — a synthetic baseline profile × a clamped product of
   illustrative event/weather/holiday multipliers (`config.py`) = a relative
   demand level per band. Baseline and adjustment are reported separately.
3. **Recommendation** (`engine.recommend_band`) — more demand ⇒ shorter
   headway, clamped to operating limits, rounded, with a deadband so small
   changes become "maintain". Reference headways come from the **official** GMRC
   timetable; the timetable itself is never edited by event hours.
4. **Explanation** — a deterministic template (no LLM) stating the change, the
   drivers, and the data caveats.

Every number that shapes a recommendation lives in `headwayiq/config.py`.

## Usage (CLI)

```bash
python -m headwayiq.cli validate      # validate fixtures, print a report (no DB)
python -m headwayiq.cli load          # create tables + validate + load fixtures
python -m headwayiq.cli status        # fixture + database readiness report
python -m headwayiq.cli init-db       # create tables only (idempotent)
python -m headwayiq.cli serve [PORT]  # run the dashboard (default port 8000)
```

The database is written to `data/headwayiq.db` (git-ignored, regenerated by
`load`). Pass a path as the last argument to use a different file.

## Honesty & limits

Recommendations are **decision support, not an operating order**. Demand and the
adjustment multipliers are illustrative; a daily ridership total is not hourly
station-level demand, and service frequency is not ridership. Validate against
live gate/AFC counts before any operational use.
